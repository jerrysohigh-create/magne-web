Hardware, ports, buttons and package contents

Distinguish physical ports, on-screen controls and supplied accessories. Specification illustrations are not evidence of a hands-on procedure.

Device and packaging → Official MAG1 specifications

Before you start

  • Have the phone and packing list ready
  • Keep ports dry
  • Do not insert the SIM eject tool into a microphone opening

Reference steps · see recorded scope below

  1. Compare the package label—model MA1, product MAG1—with the order. Do not publish the IMEI or serial number.
  2. Identify the USB-C port, 3.5 mm headphone jack, SIM tray, cameras and side buttons. Their exact positions still require an annotated hardware check; do not insert an eject tool based on a guess.
  3. Check the packing list for the phone, cable, charger, SIM eject tool and any NFC accessories. A feature listed on the website does not mean its accessory is included in every shipment.
  4. Identify the power and volume buttons from the device markings. Short presses, long presses and button combinations each need verification on this model.
  5. Remove transport protection before first use. Check the glass, ports and accessories for damage; contact the seller if anything is damaged.

16 October supplement · MAG1WW60-1 development software

  • The sample reports a 12 GB RAM class; Linux exposes about 11.14 GiB. Approximately 6.91 GiB of zram is compressed swap, not extra physical RAM.
  • The storage device identifies as WDC SDINFDO4-512G and reports UFS 3.1. Its main block device is about 512.083 GB; /data is about 464.00 GiB before considering used space. These are different units and allocation layers, not a throughput benchmark.
  • The display interface reports 1080 × 2388 and 60/120 Hz modes. The 60 Hz snapshot does not remove the separately observed 120 Hz mode. HDR types are declared capabilities, not measured brightness or certification.
  • This sample has no verified Type-C display output or working ToF ranging. A VL53L0 device object is unbound; the DP transmitter and PTN38003A redriver nodes are disabled. Node presence is not an accessory compatibility result.
  • UMP9620 audio-codec binding supersedes the inference from the legacy sc2730 sound-card name. The wireless-charger names CPS4021/CPS4201 differ and still require BOM confirmation. Exact component models are not substituted for functional tests.

GPUMali-G57; OpenGL ES 3.2. Driver: mali. Reported devfreq levels: 384 / 512 / 680 / 850 MHz.The initial scan sampled 384 MHz; the later translation test sampled 384, 680 and 850 MHz. Rendering also uses the GPU; these readings do not prove AI GPU execution.

The 1 GHz entry is a listed level, not a measured operating peak.

What has run on the NPU?

Local call translation has direct NPU execution evidence: enabling translation increased driver task counters, while the LLM service held /dev/vha0 open and mapped Qwen2.5-1.5B-Instruct-UNI. The user confirmed translation output. The second run added 15,121 completed tasks including tail processing; tasks are not tokens, and cumulative execution time is not user-perceived latency.

The initial driver study did not isolate Internet access. A later 10086 DEMO produced new Chinese recognition and English translation with Wi-Fi and mobile data disabled. That supports the tested local translation path; it does not establish measured TOPS, tokens/s, NPU clock calibration, GPU AI execution or joint CPU/GPU/NPU execution of the same model. SE — secure element, wallet interfaces and verification limits

Evidence dated 16 October 2026: MAG1WW60-1 development software, system build MAG1WW60-1; wallet USERDEBUG 1.2.15. The service observations and static code findings below are distinct from successful wallet transactions.

ItemObserved evidenceInterpretation and limits
SE availabilityThe system scan reported eSE1 with mIsConnected=true. Android OMAPI ISecureElementService / com.android.se and android.hardware.secure_element@1.2-service.hed were running.This confirms reported connectivity and the service chain, not successful execution of every wallet operation. The HAL interface version 1.2 is not a COS version.
Wallet integrationThe app uses Android OMAPI SEService / Reader / Session / Channel and the HED OSU SDK (OSU-SDK-1.2.3).Static paths include PIN verification, seed/mnemonic generation and import, public-key retrieval and signing. The audit did not execute APDU commands, create/import a wallet or sign/broadcast transactions.
COS and appletsThe SDK provides COS-version query, upgrade and recovery APIs; wallet code references seed and coin applets.The current COS version and installed applet inventory were not queried. APIs in the APK do not establish the state or security properties of the chip firmware.
Exact chip specificationsHED service names and the hednfc binding are available as integration evidence.The exact SE part number, CPU architecture, physical clock, memory capacity and EAL certification remain unverified. CIU98M50, SC300 or 120 MHz must not be presented as detected device specifications without matching vendor evidence.
TEE and PIN protectionThe separate platform TEE reports Unisoc Trusty v2.1.1. Wallet code requests AndroidKeyStore AES/GCM protection for a saved PIN with user authentication.Trusty v2.1.1 is not the SE COS version. The specific key securityLevel and hardware backing were not attested; the entire Android wallet must not be described as executing in the TEE.
StrongBox and NFC backupStrongBox was not declared in the inspected feature list. NFC backup uses a separate external card.Missing StrongBox declaration does not disprove an SE, and does not establish where a particular Keystore key resides. The external backup card, embedded SE and platform TEE are distinct components.

How it fits into the wallet

Wallet signing path in code: Android transaction preparation and confirmation → OMAPI / HED SE HAL → embedded SE and wallet applet → Android assembles and broadcasts the signed transaction. PIN protection follows a separate AndroidKeyStore / KeyMint platform-service path.

The app handles mnemonic plaintext for display/import/backup, so the current implementation does not support the claim that a mnemonic never leaves the secure element. Neither SE-backed trusted transaction display nor private-key non-exportability was established by this audit. A functioning SE service also does not certify the security of the Android app. See the wallet chapter for the development-build review status.

Vendor evidence still needed: matching part number/BOM and certificate scope; COS and applet versions; key-export boundaries; PIN retry/lockout behavior; firmware signature verification and anti-rollback; and trusted input/display design. This section publishes no device serials, APDU payloads, PINs, mnemonics or private keys.
