Before you start

  • A test account and clearly defined network conditions
  • No test wallet is available for this review
  • Do not submit transactions, staking, purchases, transfers or asset approvals

Steps

  1. com.magicalhash.mine, version 1.2.15, was found as a user-installed package. It is not automatically classified as a factory-installed mining component.
  2. Check individually whether the app provides node linking, running status, rewards, claiming, staking and exit buttons. No service operation has been opened in this review.
  3. Check the domain and network before connecting a DApp wallet. Connecting alone may reveal an address; do not capture a personal wallet.
  4. For AgentPay entries, verify current Preview / Sandbox / Testnet labels and the service version. Website descriptions do not establish production payment integration on the phone.
  5. Document signing, approval and on-chain confirmation separately. Stop before confirmation unless the test scope is clearly defined.
  6. Record rewards, balances and earnings only from actual service evidence. Do not fill test results with marketing figures.

Troubleshooting

  • Network error: check the app's current configuration and service status
  • Unexpected balance or reward: check the network, address, timestamp and data source first
  • Entry missing: record its absence for that version; do not invent it

Device wallet binding: client-code reference

The installed device-binding app, version 1.2.15, was examined without running a binding operation. Its login path involves a security-chip PIN check; the inspected login and binding paths did not show a Google-account prerequisite. This is a limited code finding, not a guarantee for every service version.

  • The client accepts a wallet address in EVM format. Passing a format check does not verify control of that wallet.
  • The app reads a chip identifier, then requests a fresh challenge from the binding server for that device and address.
  • It signs the challenge-related data through the security chip and verifies the returned data locally.
  • It submits the binding data and signature. The client saves a binding result only after both the HTTP request and the business response succeed; it can later query the server’s current record.
  • No binding, signature or server request was executed. The actual service configuration and reachability, this phone’s binding state and the binding time remain unverified.
  • A displayed binding time can fall back to the phone’s clock when the server omits it. It is not automatically a server activation timestamp. A saved chip identifier also does not establish successful binding.
  • Client error branches cover an already-bound device or address. Server-side one-to-one rules, unbinding and changing the linked wallet still need official confirmation.
  • This client flow does not establish an on-chain registration, warranty start date, node qualification or reward entitlement.
