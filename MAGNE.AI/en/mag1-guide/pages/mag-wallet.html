MAGNE Wallet: versions, networks and safe preparation

Blockchain network support

MAGNE Wallet’s supported blockchain network list will continue to be updated, with more networks added over time. MHASH L2 and the MAGNE L1 testnet have already been added to the supported network list. Please refer to the network list in the latest wallet version for current availability.

Check the installed build and network before using a wallet. The current 1.2.15 analysis identifies implemented paths and limitations; it is not a completed transaction test or a production security approval.

MAG1WW60-1 · dated captures available

This chapter uses MAG1WW60-1 evidence only. Reference steps are separate from the actions actually recorded.

Manage wallet → Add wallet → review choices → close; creation and financial operations remain untested.

Before you start

  • This analyzed build is for controlled testing pending engineering fixes and re-verification; do not treat it as approved for real-asset use.
  • No test-wallet creation, import, signing, transfer or NFC recovery was performed in this integration.
  • Required conditions include the correct app/firmware, a compatible NFC card for card workflows, and camera permission for scanning.

Reference steps · see recorded scope below

  1. Check the phone firmware and the wallet package/version first. The 16 October sample is MAG1WW60-1 userdebug with com.magicalhash.wallet 1.2.15; its underlying factory package is 1.2.14. The USER and USERDEBUG packages share code but have different signatures.
  2. Creation, phrase import, account management, PIN changes and NFC backup/restore have code paths. Their exact screens and button sequence still need verification on this build; no successful creation or restoration is claimed here.
  3. Before any future test, confirm that the wallet has no real assets, identify the network and compatible card, and keep recovery phrases, private keys and PIN entry out of screenshots and recordings.
  4. Review the network table below. A testnet flag does not force every network to a testnet, and a token ticker is not enough to identify the network.
  5. Use only the connection and authorization details actually shown by the app. Inspect the DApp origin, requested network, signing account and amount; cancel unexpected requests. Do not interpret a connection or a risk message as a successful or safe transaction.

Cancel, exit and restore

Go back or cancel authentication. Creation, import, recovery and transactions were not performed. Do not clear wallet data.

Troubleshooting

  • Scan does not open: check camera permission for the active user. The sampled user had not granted it; this is not proof that scanning is absent.
  • Network or balance differs: verify mainnet/testnet, exact network ID and RPC. MAGNE/MHASH configurations are testnets; USE_TESTNET does not apply uniformly.
  • WalletConnect rejects a chain: compare the DApp request with the initial approved chain list; custom-network support still needs integration testing.
  • Biometrics unavailable: cancel a sensitive operation and seek supported authentication guidance. Do not assume every signing path always forces a second fingerprint check.
  • NFC recovery fails: confirm card compatibility and backup version; do not overwrite the only backup or clear wallet data.
  • NFT page is empty: the analyzed asset tab is still marked developing.

Limits and versions

Static analysis found unresolved security issues. USER and USERDEBUG 1.2.15 share the relevant code; changing the signature alone is not a fix. SE participation does not make the whole Android app a trusted environment. No user-data leak or remote asset theft was demonstrated. Engineering fixes and asset-free re-testing are required before a production-use judgment.

The project statement “one HD set + 255 software wallets” and the code constants of 20 wallet indices / 100 accounts describe different concepts. Neither is used here as a verified SE capacity or as a replacement for the other; vendor mapping and boundary testing are pending.

SE, TEE and the NFC card have different roles

Wallet signing code calls OMAPI / HED SE interfaces. Biometric PIN protection uses Android Keystore / KeyMint, with Trusty services present. The NFC backup card is an external device. Android still handles transaction construction, confirmation, networking and decrypted recovery phrases during display/backup; “the recovery phrase never leaves the SE” is not supported. No independent trusted transaction display, exact SE model, certification, retry policy or anti-rollback behavior was established.
